Every time a browser opens a secure connection, it introduces itself with a handshake message called a ClientHello. The message lists which encryption options and extensions the browser supports, in a specific order. Real Chrome sends a very specific ClientHello, and that pattern changes as Chrome updates.

Tools that pretend to be Chrome (for testing, automation, or scraping) have to copy that pattern exactly. When Chrome changes and the tool doesn't, the tool stands out. Stale captures what real Chrome sends, compares it against the popular impersonation libraries, and shows which ones match and which have fallen behind.

Why this matters

If you build clients or automation

Sites increasingly check the handshake before they look at anything else. If your library is a few Chrome versions behind, your traffic can be flagged before a single page loads. Check here before you pick a library or blame your proxies.

If you defend a site

Knowing exactly what current Chrome sends, and which popular libraries can and can't copy it, tells you which fingerprints are real users and which are tools pretending. Stale gives you that reference, built from real captures and compared field by field.

Methodology

  • Chrome reference: …, captured with fresh browser profiles against a local capture server that records the raw ClientHello, HTTP/2 frames and the QUIC/HTTP/3 handshake (JA4 per the FoxIO spec, cross-checked against tshark). The three Chrome variants are separate real captures: default, --disable-features=TLSTrustAnchorIDs, and the forced post-quantum experiment group.
  • Libraries: each profile makes real requests to a TLS echo endpoint (…). We normalize the ClientHello and HTTP/2 frames and diff them field by field against the reference. GREASE values and extension order are ignored, as in JA4.
  • Resumption: tested only where noted, by opening a new connection on the same client and checking for pre_shared_key.
  • HTTP/3: every library profile with an HTTP/3 client makes a real HTTP/3 request to the same local QUIC endpoint that captured Chrome's QUIC fingerprint (…). We record its QUIC JA4, transport parameters and HTTP/3 SETTINGS and diff them against Chrome. Libraries without an HTTP/3 client are marked "no HTTP/3 support". Chrome was forced onto HTTP/3 against our own local test server, not a live public site, so a real site's setup could change some details of Chrome's HTTP/3 fingerprint.
  • Every value comes from a real capture. Anything we didn't measure is shown as "not tested", never guessed. Leaderboard data generated ….
